## 0. The A/B run that decides whether v1 ships (spends Claude plan usage)

- **What:** `bench/ab/run.py` runs Claude Code headless on Loc-Bench issues with and without the plugin and compares tokens, tool calls and whether the right files were named (ADR-011). The design's gate: the best rung gives at least 20% fewer tokens or tool calls than no plugin, with no drop in hit rate.
- **Why it waits:** every session spends your plan usage. A pilot of eight sessions (about $1.85) proved the harness and showed the cost: about $0.30 a session on the mid model, so 60 sessions are about $20. It also showed that rung 1 as first written was followed in only two sessions of four, and that run-to-run differences of 20 to 40% occur without Aleph being called at all (ADR-011). The full run is yours to size and start.
- **Decisions that are yours:**
  1. *The baseline.* The gate says "than no plugin"; the design's ladder calls L0 "the engine without the mod". `none` answers whether Aleph helps at all, L0 what the steering adds.
  2. *The shape.* Four rungs at 30 tasks each cannot read a 20% gate (run-to-run noise is about a factor of two; ADR-011). Two arms with 60 tasks, or 30 tasks twice, come closer for the same number of sessions.
  3. *The model.* The pilot used the cheap and the mid model. The gate should be read on the model you work with.
  4. *The ten tasks from your own repositories* that the design asks for need your questions (as entry 2 below).
- **Arms:** `none`, `L0`, `L1n` (rung 1 without the pointer in Grep and Glob: what the pilot ran), `L1`, `L2`, `L3`. Running the same command twice appends a second run of the same tasks; the report then pairs on the mean of a task's runs.
- **How to start it** (example: no plugin against rung 1, 30 tasks, the mid model, at most 60 sessions):

      uv run --group bench python bench/ab/run.py run bench/data/benchc --arms none,L1 --count 30 --model sonnet --max-sessions 60

  Results are appended to `bench/data/results/ab/`, one line per session, so a run can be stopped and its report made from what is there: `bench/ab/run.py report <file>`.
- **Also yours, one minute:** run `claude --plugin-dir plugin` once in this repository, interactively. Claude Code then writes the type declarations for your build into `plugin/.claude-plugin/types/`; the mod was written without them (ADR-011). And allow the engine's tools (`"mcp__plugin_aleph-zero_aleph__*"` in `permissions.allow`), or rungs 2 and 3 add nothing.
- **Status:** harness and pilot done; full run not started.
- **How to do it (advice of 2026-10-12, three voices kept apart).**
  - *What is written elsewhere:* Bjarnason, Silva and Monperrus, "On Randomness in Agentic Evals" ([arXiv:2602.07150](https://arxiv.org/abs/2602.07150)): 60,000 trajectories on SWE-Bench-Verified; a single run's pass@1 moves by 2.2 to 6.0 points depending on which run it is; they ask for several runs per task and a power analysis before reading small differences.
  - *The advisor:* at least two runs per arm and a paired test; the smallest design worth its cost is 2 arms × 30 tasks × 2 runs.
  - *agy:* do not commit to 120 sessions up front. Run 2 arms × 30 tasks once, look first at whether the agent called Aleph at all in the plugin arm (at half compliance a 20% effect reads as 10%), and only then pay for the second run of each task.
  - *Mine:* agy's order with the advisor's size: one pass of 60 sessions, a look at compliance, then the second pass. The harness now supports that: `bench/ab/run.py pause|resume|stop|status <results directory>` from any shell, and `--take-up FILE` runs only the sessions an interrupted run is missing (it refuses a file of another seed or count, counts only the missing sessions against `--max-sessions`, and does not ask a session a third time after two failures). But the candidate pool that reaches it (300) was chosen on those same questions; at the first pool (50) the gain was +3.2 and the gate was not met (ADR-002). The 165 questions in the repositories below have not been seen: if they also show a gain near or above 5 points, the verdict stands; if not, it should be switched off (`src/aleph_zero/dense_policy.py`, one line).
- **Heat:** `prepare` looks at the chip's temperature after every batch and pauses while it is at 95 °C or above, or while macOS reports thermal pressure, until it is back under 80 °C (`--temp-limit` changes the limit); its last line says the highest reading and how often it paused. To watch from another terminal: `uv run python bench/tools/temps.py --watch 30`. The held-out check does not pass, and vectors are off by default for Python.** `prepare` ran from 22:13 to 02:16 (165 of 165, chip at 78 °C at most, no waits to cool; later commits of a repository share most of their content, which is why it was hours and not a day), and `run` started by itself. ## 3. Git's untracked cache in the owner's repositories

- **What:** `git config core.untrackedCache true`, per repository.
- **Why it waits:** it changes the owner's git configuration, so Aleph does not do it. It takes the per-query git check from about 74 ms to 26 ms on a 7,000-file repository (ADR-008). `aleph doctor` shows whether it is on.
- **A way that changes no configuration (found 2026-10-12):** `git update-index --untracked-cache` keeps the cache in that repository's index only. Measured on Django's 6,833 files: Aleph's check takes 60 ms without it and 10 to 20 ms with it. `aleph doctor` now names this way and recognises a cache that is on this way.
  - *agy* proposed that Aleph pass `-c core.untrackedCache=true` on its own git calls. Measured: that does nothing, because Aleph runs git with optional locks off so as never to contend with your own git commands, and the cache is only written by a command that may write the index. Making Aleph's call write your index is the same change by another road, and stays yours to make.
  - Git also has a built-in file-system monitor ([`core.fsmonitor`](https://github.blog/engineering/infrastructure/improve-git-monorepo-performance-with-a-file-system-monitor/), macOS and Windows), which works together with the untracked cache; it is a configuration setting and starts a daemon per repository, so it too is yours.

## 7. Left out of M3 on purpose (ADR-010)

- **Searching a directory that is not a git repository.** *Built in M10* (ADR-010, "A directory that is not a repository"): searched as it is on disk, with a rule about what is never walked (a home directory, the top of a disk, more than 20,000 files) and what is left out (everything hidden, tool directories, repositories inside it).
- **Things that need Linux:** giving the vector file's free blocks back there (`fallocate`; written, never run: macOS is what was measured); file names that are not valid UTF-8 (cannot be created on macOS); reading a session's own memory there is written (`/proc/self/smaps_rollup`) but has only been run on macOS; the network-filesystem check reads `/proc/self/mountinfo` and is likewise untested there; a file-system watcher, if it passes the "change, then ask at once" test.
- **Two installed versions of Aleph with different chunkers sharing one index** took turns re-indexing everything. *Fixed in M10:* the older one now stops with one sentence saying a newer version has read this content, as it does for a newer schema; the newer one reads older content again once, as before. The sentence says how to start over with the older version (delete the cache directory), and `aleph doctor` reports the same.
- **The vector file gives its disk back** *(done 2026-10-12, ADR-010)*. It still does not get shorter (a session may have its tail mapped), but the blocks under free rows go back to the file system after a collection: 153.6 MB to 51.2 MB on disk for a large abandoned branch, measured. Free rows scattered among rows in use stay until used again; rewriting the file to close those gaps was weighed and not built (a schema change and a protocol for every reader, for little).
- **A trigram index for text written without spaces** (Chinese, Japanese, Korean): no repository in use needs it.
- **Plain values of object literals** (`limit: 10`) are not listed as symbols; functions in them are.
- **Left as they are after the M3 review, with their cost:** vector rows are flushed with `fsync`, not macOS's stronger `F_FULLFSYNC`, so after a power failure (not a crash) a row could hold older bytes than the index says; a cache directory on a network home directory is not detected; a collection round killed half-way waits a day for the next; while a session's own background thread is embedding, each of its queries re-checks the whole view (about 2 ms on Django).
