## 3. Git's untracked cache in the owner's repositories

- **What:** `git config core.untrackedCache true`, per repository.
- **Why it waits:** it changes the owner's git configuration, so Aleph does not do it. It takes the per-query git check from about 74 ms to 26 ms on a 7,000-file repository (ADR-008). `aleph doctor` shows whether it is on.
- **A way that changes no configuration (found 2026-10-12):** `git update-index --untracked-cache` keeps the cache in that repository's index only. Measured on Django's 6,833 files: Aleph's check takes 60 ms without it and 10 to 20 ms with it. `aleph doctor` now names this way and recognises a cache that is on this way.
  - *agy* proposed that Aleph pass `-c core.untrackedCache=true` on its own git calls. Measured: that does nothing, because Aleph runs git with optional locks off so as never to contend with your own git commands, and the cache is only written by a command that may write the index. Making Aleph's call write your index is the same change by another road, and stays yours to make.
  - Git also has a built-in file-system monitor ([`core.fsmonitor`](https://github.blog/engineering/infrastructure/improve-git-monorepo-performance-with-a-file-system-monitor/), macOS and Windows), which works together with the untracked cache; it is a configuration setting and starts a daemon per repository, so it too is yours.

- **Measured again on a large repository (2026-10-13): the first questions after a checkout cost far more than was written.** On a fresh worktree of vscode (5,176 files) every question pays 340 to 390 ms of `git status` until some ordinary git command has run in that worktree (36 ms after one; 13 ms with the untracked cache). ADR-008 said "up to 50 ms". Aleph's own commands do not heal it (`aleph index`, `aleph update` and its hooks write no index, on purpose). In a worktree you work in, your shell prompt or editor heals it within seconds; a worktree only Aleph reads stays slow. Two things you could choose, neither built: the untracked cache as above (`aleph setup` offers it); or one line `git status >/dev/null` in the `post-checkout` hook beside the line `aleph update --print-hook` prints, which takes git's index lock for a moment right after your own git command has ended.
- **A cost of its own on repositories with very many files (found the same evening, and reduced):** matching a long question's words against the paths read every path into words by itself, on the first question of a process and again on the second: 123 ms on babel (26,622 files). The words are now read by the directory and by the file's name (far fewer of both than files): babel 47 ms, vscode 18 to 12, trino 38 to 23, material-ui (42,429 files, nearly all names different) 193 to 135. The maps are the same, checked on the real paths of six repositories. What is left on a repository like material-ui is one reading per file name; not taken further.
